# Deploying Civil

Infrastructure is Terraform; the deploy itself is one script. PRD §2 asks for exactly
one of each.

## One-time setup

Already done for `lantern-civil`, recorded here so a clean checkout can repeat it.

```bash
gcloud projects create lantern-civil --name="Civil"
gcloud billing projects link lantern-civil --billing-account=<ACCOUNT_ID>
gcloud services enable run sqladmin secretmanager iap cloudbuild \
  artifactregistry compute iamcredentials storage --project=lantern-civil
gcloud beta services identity create --service=iap.googleapis.com --project=lantern-civil
gcloud storage buckets create gs://lantern-civil-tfstate \
  --project=lantern-civil --location=us-central1 \
  --uniform-bucket-level-access --public-access-prevention
gcloud storage buckets update gs://lantern-civil-tfstate --versioning
```

Then:

```bash
cp infra/terraform/example.tfvars infra/terraform/terraform.tfvars   # edit it
terraform -chdir=infra/terraform init
terraform -chdir=infra/terraform apply
```

## The one manual step: the Google OAuth client

**This cannot be scripted,** and it is the only part of the deploy that is not in
Terraform. Creating an OAuth client is an account action, and its secret should never
pass through a plan, a state file, or a terminal transcript.

### 1. Consent screen

Console → **APIs & Services → OAuth consent screen** (newer consoles: **Google Auth
Platform → Branding**) in the `lantern-civil` project.

- User type **External** — there is no Internal option without an organization.
- App name and your email in both contact fields. No scopes or domains are needed;
  Civil requests only `openid email profile`.
- Leave it in **Testing** while it is just you and people you add as test users.
  Publishing triggers a verification review that these scopes do not need — but note
  that in Testing, only listed test users can sign in, which is a de facto allowlist.
  Publish when you actually want open signup.

### 2. OAuth client

Console → **APIs & Services → Credentials → Create credentials → OAuth client ID**,
type **Web application**.

| Field | Value |
|---|---|
| Authorised JavaScript origin | `https://civil-35752011174.us-central1.run.app` |
| Authorised redirect URI | `https://civil-35752011174.us-central1.run.app/auth/google/callback` |

The redirect URI must match byte for byte — Google compares it exactly, and a
trailing slash is a different URI. `terraform output oauth_redirect_uri` prints the
authoritative value.

### 3. Write the values into Secret Manager yourself

The containers exist and the runtime service account can already read them; only the
values are missing. Piping from stdin keeps the secret out of your shell history:

```bash
gcloud secrets versions add civil-google-client-id --project=lantern-civil --data-file=-
gcloud secrets versions add civil-google-client-secret --project=lantern-civil --data-file=-
```

Paste the value, then press Ctrl-D. The session signing key was generated by
Terraform and needs nothing.

### 4. Finish

```bash
terraform -chdir=infra/terraform apply
./scripts/deploy.sh
```

### Symptom if you skip it

The Cloud Run revision fails to start, because a secret reference with no version
cannot be resolved. Logs say the secret version was not found — not that OAuth is
unconfigured.

## Every deploy after that

```bash
./scripts/deploy.sh
```

It builds the image with Cloud Build, tags it with the current git sha (suffixed
`-dirty` if the tree is not clean), runs migrations as a Cloud Run job from that
same image, and only then updates the service. Migrations before deploy is the safe
ordering for additive migrations — and additive is a discipline, not something
Terraform enforces.

## Cost

At the tier provisioned here, roughly $20–25/month: Cloud SQL `db-f1-micro` on the
ENTERPRISE edition, plus one always-warm Cloud Run instance.

One thing to know before M4: the warm instance has `cpu_idle = true`, so its CPU is
throttled between requests. That is fine for serving, but §12's long-running,
request-independent job ownership needs `cpu_idle = false`, and always-allocated vCPU
is billed at roughly ten times the idle rate. Budget for that when M4 lands rather
than being surprised by it.

## Tearing down

```bash
terraform -chdir=infra/terraform apply -var db_deletion_protection=false
terraform -chdir=infra/terraform destroy
```

The state bucket and the project itself are outside Terraform and must go by hand.
